# yt-dlp channel tools

Утилиты для работы с коллекциями видео, скачанными с YouTube-каналов
(`yt-dlp` сохраняет файлы вида `Название [VIDEO_ID].mp4`).

## Структура проекта

```
yt-dlp/
  _books/              ← книги: сканы страниц и извлечённый текст (в git,
    Wojna_Futbolowa/     в отличие от _channels/ — результаты OCR не
      pages.txt          восстанавливаются повторным скачиванием)
      pages_expanded.txt ← полный список URL страниц Archive.org
      pages_extracted/ ← PNG-скриншоты разворотов
      pages_text/      ← распознанный текст (Markdown, по разворотам)
      book/            ← собираемый вручную документ
  _channels/           ← папки отдельных YouTube-каналов (не в git)
    _Handle/
      _cache/          ← кэш канала: videos.json, playlists.json, video_playlists.json
      _playlists/      ← папки плейлистов (имена без ведущего _)
      _summaries/      ← summaries по датам: YYYY-MM-DD/_hh_mm_*.txt/xlsx
      ...
  misc/                ← прочие коллекции, не привязанные к каналу (не в git)
  _run_scripts/        ← bat-файлы корня проекта: проверка плейлистов,
                         поиск канала по описанию, синхронизация путей в
                         bat-файлах, OCR очередной порции книги (в git,
                         в отличие от _run_scripts внутри папок каналов);
                         логи запусков — в _run_scripts/_logs/ (не в git)
  prompts/             ← расшифровки чатов с агентом и их читаемые копии
                         (не в git)
  src/                 ← исходники Python: пайплайн YouTube-каналов лежит
                         плоско (его пути зашиты в сгенерированные bat-файлы
                         каналов и в exe), новые функциональные модули
                         добавляются подпапками
    book_ocr/          ← модуль сканирования и OCR книг (см. раздел «Книги»)
  scripts/             ← готовые exe для запуска
  readme.md
```

## Пайплайн

0. **`find_youtube_channel_by_descr`** — поиск YouTube-канала по свободному
   текстовому описанию; по подтверждению создаёт папку канала, запускает
   шаг 1 и генерирует bat-файлы «транскрибировать + отредактировать
   очередное видео» (см. раздел ниже)
1. **`get_summary_for_channel`** — summaries канала в `.txt` / `.xlsx` (+ столбец плейлиста)
2. **`download_videos`** — скачивание видео канала через `yt-dlp` (бесплатно)
   сразу в папки плейлистов и в конвенции имён проекта
2a. **`download_presentations`** — презентация, выложенная лектором в
   комментарии под видео, в папку `PRESENTATIONS/` (бесплатно); опционален,
   вызывается сам из шага 2 и по флагу из шага 5
3. **`organize_by_playlists`** — раскладка скачанных файлов по плейлистам
4. **`transcribe_videos`** — транскрибирование скачанных видео (OpenAI audio API);
   в удалённом режиме (`--from-youtube` / `--url`) видео берётся прямо с YouTube
   (скачивается только аудио), а флаги `--slides` и `--edit` продолжают запуск
   шагами 5–6 и 7
4a. **`check_transcripts`** — отчёт о подозрительных местах транскрипта
   (офлайн, без обращений к API); опционален
4b. **`silences`** — паузы записи в сайдкар рядом с видео (офлайн, ffmpeg);
   опционален: шаг 7 при необходимости снимает их сам
5. **`extract_slides`** — извлечение слайдов из слайдовых видео (PySceneDetect)
6. **`text_from_slides`** — извлечение текста из слайдов в `slides.json` (OpenAI vision)
7. **`create_final_docs`** — финальные отредактированные документы (.md/.docx/.pdf);
   шаги 5–6 опциональны: без слайдов (`--no-slides`) оглавление строится по
   таймкодам видео

Шаги 5–6 нужны только для слайдовых видео; summaries (шаг 1) в автоматическую
цепочку не включаются — по ним пользователь сам решает, какие видео пускать
дальше по пайплайну.

Каждая папка YouTube-канала в `_channels/` (на любом уровне вложенности)
содержит обязательную подпапку `_playlists/`. Папки-контейнеры, которые
объединяют несколько каналов, `_playlists/` не имеют; внутри них лежат либо
другие контейнеры, либо папки отдельных каналов. Контейнер для нового
канала задаётся строкой `rem CHANNEL_PATH=...` в
`_run_scripts\add_youtube_channel_by_descr.bat` (шаг 0); уже существующий
канал переносится в другой контейнер вручную, после чего пути в bat-файлах
чинит `_run_scripts\synchronize_folders_in_bats.bat` (см. раздел ниже).

Имя папки канала формируется из `@handle` с ведущим подчёркиванием, например
`@Ekaterina_Schulmann` → `_Ekaterina_Schulmann`. В скриптах и `*.bat`-файлах
канал задаётся путём относительно `_channels/` (например `_Autotesting` или
`AI_for_Game_Design\_BuildingAeon`).

Имя папки плейлиста — название плейлиста строчными буквами, с
транслитерацией кириллицы и заменой всего прочего на `_`
(`slugify_playlist_name`). Отдельно оговорены названия языков, кончающихся
знаком препинания: `#` и `+` папке не достаются, и «Advanced C#»
превращалось в `advanced_c` — в другое слово, да ещё и совпадающее с
«Advanced C». Теперь такие названия выписываются словом:
`advanced_c_sharp`, `f_sharp_...`, `cpp_...`. То же и для имён каналов.

Само по себе `C#` — ещё и нота (до-диез), поэтому решает контекст: перед
заменой читаются все названия плейлистов канала и его имя. Замена
пропускается, если музыкальных слов там больше, чем компьютерных
(«Piano lessons», «Chords and scales» → `c_minor`); при молчании с обеих
сторон замена делается — этот проект качает лекции, а не сольфеджио.
Затронуто только отдельно стоящее название: `C#7` — аккорд не реже, чем
версия языка, и его не трогают. Папку, созданную по прежнему правилу,
очередная синхронизация плейлистов переименует сама (`advanced_c` →
`advanced_c_sharp`) — с сообщением в логе и не трогая чужую папку, если
на прежнее имя есть свой плейлист.

Просмотр дерева: `python src/check_playlists.py --layout`.

## Кто что решает

Шаги 4–7 состоят из полутора десятков решений, и каждое принимает либо код,
либо модель. Граница между ними одна: решение отдаётся коду, если его можно
проверить, не читая текст глазами. Тогда оно ничего не стоит, повторяется
от прогона к прогону и покрывается тестом. Всё остальное — вопрос смысла, и
за него платят.

| Что решается                              | Кто решает                | На чём                                                          | Чем проверяется                                                     | Цена                                   |
|-------------------------------------------|---------------------------|-----------------------------------------------------------------|---------------------------------------------------------------------|----------------------------------------|
| Какие слова сказаны                       | `whisper-1`               | аудио, `terms.txt` подсказкой                                   | `check_transcripts`: три сигнала                                    | $0.36 за час записи, на каждый язык    |
| Где кончается абзац                       | код (`transcribe_videos`) | паузы записи, длина в словах                                    | `_test_paragraphs.py`, отчёт о длинных абзацах                      | 0                                      |
| Где сменился слайд                        | код (PySceneDetect)       | кадры, центральная часть                                        | `scenes.csv` и картинки глазами                                     | 0                                      |   
| Когда на странице появился пункт          | код (`extract_slides`)    | карты краёв кадров, раз в две секунды, мимо окна вебкамеры      | `_test_reveals.py`, проба: 10 моментов против 8 пунктов на странице | 0                                      |

| Пунктуация, падежи, термины, формулировки | `gpt-4o`                  | оба транскрипта и глоссарий                                     | плотность знаков, вопросы с точкой, вычитка человеком               | $0.03–0.05 на раздел, ~$0.40 на лекцию |

| Длина абзаца в результате                 | код                       | 200 слов, ближайший конец предложения                           | отчёт о том, что разрезать не удалось                               | 0                                      |
| «ё», «имею в виду»                        | код                       | списки бесспорных написаний                                     | `_test_punctuation.py`                                              | 0                                      |
| Редактировать ли раздел заново            | код                       | версия правил, диапазон времени, полнота                        | оценка стоимости перед запуском                                     | определяет цену прогона                |
| Как выглядит `.docx` и PDF                | код и внешний Word/WPS    | шаблон стилей                                                   | глазами                                                             | 0                                      |

Практическое следствие: от смены модели зависят ровно четыре строки таблицы
— чтение слайда, структура документа, разбиение на подразделы и само
редактирование. Остальное к модели равнодушно, и сравнивать модели надо
только на них. Мерить это дёшево: раздел выбрасывается из
`edited_sections.json` и переиздаётся один — около пяти центов, а версия
правил (`EDIT_RULES_VERSION`) и кэш делают сравнение воспроизводимым.

Чего сейчас не решает никто — известно и измерено (см. «Пунктуация и
грамматика»): окончание английского слова в русском падеже (`benefit-ы`,
`quality gate-ов`) распознаватель отсекает, а редактор не восстанавливает,
и ослышку вне глоссария («гид» вместо Git) не чинит ни код, ни модель.
Первое — задача для промпта, второе — для `terms.txt`.

## Книги: `src/book_ocr/`

Отдельный от YouTube-пайплайна модуль: оцифровка книги, взятой на
archive.org по Controlled Digital Lending (Р. Капущинский, «Wojna
futbolowa», по-польски). Данные — в `_books/Wojna_Futbolowa/`.

Пайплайн из двух шагов:

1. **`scan_pages.py`** — скриншоты разворотов книги в
   `_books/<книга>/pages_extracted/`. Требует Edge с включённым remote
   debugging и активным займом книги: сначала запустить
   `_run_scripts\book_start_edge_for_scan.ps1`, в открывшемся окне Edge
   выполнить Borrow, затем `python src\book_ocr\scan_pages.py`.
2. **`ocr_claude.py`** — распознавание польского текста со скриншотов
   (Claude Sonnet vision, ключ `ANTHROPIC_API_KEY` в корневом `.env`) в
   `_books/<книга>/pages_text/*.md`. Постобработка локальная: снятие
   внутристраничных переносов, перенос слова на границе страниц
   сохраняется как в книге, строки заворачиваются по средней ширине
   строки оригинала (+3 символа) с выравниванием правого края
   добавочными пробелами.

Запуск очередной порции — `_run_scripts\book_ocr_next_batch.bat`
(размер порции задаётся переменной `BATCH_SIZE` в начале файла; лог
каждого запуска — в `_run_scripts/_logs/book_ocr_next_batch_*.log`):

```bat
book_ocr_next_batch.bat                 очередные BATCH_SIZE разворотов без .md
book_ocr_next_batch.bat overwrite-first перераспознать первые BATCH_SIZE
book_ocr_next_batch.bat page_016        BATCH_SIZE разворотов начиная с page_016
```

Другая книга — новая папка под `_books/` со своим `pages_expanded.txt`
и флаг `--book <папка>` у обоих скриптов.

## `get_summary_for_channel.exe`

### Минимальный запуск

```bat
scripts\get_summary_for_channel.exe @Ekaterina_Schulmann
```

или:

```bat
python src\get_summary_for_channel.py @Ekaterina_Schulmann
```

**Первый параметр (обязательный):** `UC…`, `@handle` или URL канала.  
**Второй параметр (необязательный, default: `bypls`):** режим или плейлист:

| Значение | Поведение |
|----------|-----------|
| `bypls` | Группировка по плейлистам (default) |
| `allpls` | Общий порядок канала, плейлисты вперемешку |
| `#A`, `#B`, … | Только указанный плейлист (алиас из `playlists.json`) |
| префикс имени | ≥3 символов, совпадает с началом ровно одного плейлиста |

Выходные файлы: `_channels/_Handle/_summaries/YYYY-MM-DD/_hh_mm_*.txt` и `.xlsx`  
Имя файла **без** имени канала; начинается с `_hh_mm_` и отражает режим/флаги.

| Шаблон | Условие |
|--------|---------|
| `_hh_mm_pls` | `--plsonly` |
| `_hh_mm_plsall` | `allpls`, без `--from`/`--to` |
| `_hh_mm_plsgrp` | `bypls` (default), без фильтра |
| `_plo` | при `--include-playlist-only` |
| `_f_N`, `_t_N` | при `--from N` / `--to N` |
| `_n_N` | при `--next N` (если `--next` задан позже `--to` или вместо него) |
| `_new` | при `--new` |
| `_pls_A` | один плейлист по алиасу `#A` |

### `--plsonly`

Только список плейлистов (остальные аргументы игнорируются).  
Создаёт `_cache/playlists.json`, если его нет. Каждому плейлисту присваивается
алиас `#A`, `#B`, … `#Z`, `#AA`, … (как столбцы Excel).

XLSX: строка 1 — `Playlists for channel <name>  (channel_id = UC… ):`,  
далее столбцы: алиас, имя канала, название плейлиста.

### Столбцы XLSX (summary видео)

| Col | Поле |
|-----|------|
| 1 | № (индекс на канале или в плейлисте — см. режим) |
| 2 | Оценка стоимости транскрибирования, $ |
| 3 | Имя канала |
| 4 | Плейлист |
| 5 | URL |
| 6 | Дата |
| 7 | Длительность |
| 8 | Заголовок |

**Строка TXT (видео):** `{index} {cost} {url} ({channel} | {playlist} : {title} ) {date} {duration}` —
если плейлист известен; иначе `{index} {cost} {url} ({channel} : {title} ) …`.  
`{index}` — номер как в XLSX (min 3 символа; шире при номерах ≥1000); при `--new` для новых видео — `new`.  
`{cost}` — оценка стоимости транскрибирования, например `$0.83`.  
Консоль: `@handle (UC…)`; в XLSX/TXT — display name канала с YouTube.

### Оценка стоимости транскрибирования

Стоимость считается по тарифу OpenAI (`whisper-1` / `gpt-4o-transcribe`,
$0.006/мин ≈ $0.36/час на июль 2026). Тариф кэшируется в **общем** для всех
каналов файле `_cache/transcription_pricing.json` в корне проекта и
перепроверяется по странице тарифов OpenAI не чаще, чем раз в 30 дней
(при недоступности страницы используется кэшированное значение).

Ключ `--lang XX` (по умолчанию `ru`) задаёт язык оригинала: для неанглийских
каналов стоимость считается за **два** прохода транскрибирования
(язык оригинала + английский), для `--lang en` — за один.

**Нумерация:** при `bypls` без `--from`/`--to` — сквозная **внутри каждого плейлиста**
(1, 2, 3… заново для каждого). При `allpls` или с фильтром — номера относительно
**baseline**-списка (`length_old`). Новые видео (после последнего запуска без `--new`)
при `--new` выводятся первыми с номером `new`.

### `--include-playlist-only`

По умолчанию summary строится по ленте **Videos/uploads** канала. Часть роликов
(часто записи эфиров) есть в плейлистах канала, но **не** во вкладке Videos —
без флага они в summary не попадают.

С `--include-playlist-only` такие видео добавляются в экспорт (в свои плейлисты
при `bypls`). Метаданные (название, длительность) кэшируются в
`_cache/video_playlists.json` (`details`); при первом запуске с флагом карта
плейлистов пересобирается, если `details` ещё нет. В имени файла появляется
суффикс `_plo`.

### `--new`

Сохраняет baseline-нумерацию (`length_old`) для запланированной поэтапной загрузки.
`--from` / `--to` считаются относительно baseline, а не текущей длины канала.
При `--new` в начало summary попадают все новые видео (номер `new`), затем диапазон
`--from`…`--to`. Без `--new` после успешного экспорта `length_old` обновляется до
текущей длины.

Пример поэтапной загрузки (шаг 2 пайплайна, 900+ видео, ~200/день):

```bat
python src\get_summary_for_channel.py @Channel allpls --from 1 --to 200
python src\get_summary_for_channel.py @Channel allpls --new --from 201 --next 200
python src\get_summary_for_channel.py @Channel allpls --new --from 401 --next 200
```

`--next N` — альтернатива `--to`: экспорт N видео начиная с `--from`
(`--to = --from + N - 1`). Если указаны оба, учитывается **более поздний** флаг
в командной строке.

### `--from` / `--to` по названию видео

Значение может быть числом или строкой **не короче 3 символов** (при пробелах — в кавычках).
Строка сопоставляется с полным названием или с **единственным** префиксом названия
в кэшированном списке; найденному видео присваивается его baseline-номер.
Если совпадений нет или их несколько — скрипт завершается, в `_summaries` пишется
однострочный notice `.txt`.

### Кэш

| Файл | Содержимое |
|------|------------|
| `videos.json` | Список видео канала, `length_curr`, `length_old`, длины по плейлистам |
| `playlists.json` | Плейлисты канала + алиасы `#A`… |
| `video_playlists.json` | `video_id → playlist title` |

**Канал без плейлистов.** Бывают каналы, у которых вкладки Playlists нет
вовсе — только видео. yt-dlp сообщает об этом ошибкой (`This channel does
not have a playlists tab`), но для проекта это не сбой, а ответ: список
плейлистов пуст, `playlists.json` сохраняется пустым, и рядом создаётся
единственная папка `_playlists/misc/` — та же, куда в остальных каналах
попадают видео вне плейлистов. Туда идут все видео такого канала. Summary
для него строится плоским списком (`allpls`) — про группировку по
плейлистам скрипт поиска канала уже не спрашивает, — а
`transcribe_and_edit_next_bypl.bat` не создаётся: группировать нечего,
и работает плоский `transcribe_and_edit_next.bat`.

**Smart refresh** (автоматически при каждом обращении):

- `length_curr` уменьшилась → аварийный полный refresh, команда прерывается (в `_summaries` — notice)
- `length_curr` не изменилась → если кэш старше 24 ч, сверка 4 видео; иначе кэш без изменений
- `length_curr` выросла → сверка со сдвигом (новые в начале); при успехе — подкачка без полного refresh

Полный refresh вручную: `python src/refresh_channel_cache.py @Channel --force`  
Инкрементальный (по умолчанию): `python src/refresh_channel_cache.py @Channel`

Флаг `--refresh` **убран**. Флаг `--new` — см. выше.

### Примеры

```bat
:: Summary по плейлистам (default bypls)
python src\get_summary_for_channel.py @Ekaterina_Schulmann

:: Общий список канала
python src\get_summary_for_channel.py @Ekaterina_Schulmann allpls --from 1 --to 50

:: Один плейлист по алиасу
python src\get_summary_for_channel.py @VladilenMinin "#A" --from 1 --to 20

:: Только список плейлистов
python src\get_summary_for_channel.py @Ekaterina_Schulmann --plsonly
```

## `synchronize_folders_in_bats.py`

Сервисный скрипт: сверяет пути, зашитые в `*.bat`-файлы проекта, с тем, как
папки лежат на диске сейчас, и правит устаревшие. Запускать после переноса
проекта в другую папку или на другой диск и после перекладывания папок
каналов по контейнерам.

### Запуск

```bat
_run_scripts\synchronize_folders_in_bats.bat
_run_scripts\synchronize_folders_in_bats.bat --check
python src\synchronize_folders_in_bats.py
```

Сам bat-файл находит проект по собственному расположению (`cd /d "%~dp0.."`),
поэтому переживает переезд проекта и не нуждается в правке. Параметр
`--check` только показывает, что изменилось бы, ничего не записывая; код
возврата 1 означает, что расхождения остались.

### Что проверяется

| Строка bat-файла | Проверка |
|------------------|----------|
| `cd /d <путь>` | Совпадает ли с текущим корнем проекта |
| `set "CHANNEL=..."` | Совпадает ли с реальным путём папки канала относительно `_channels/` |
| `set "PLAYLIST=..."` | Есть ли такая папка в `_playlists/` этого канала |
| прочие абсолютные пути | Существуют ли они внутри проекта |

Канал определяется по расположению самого bat-файла: скрипт поднимается от
него вверх до ближайшей папки с `_playlists/` — это и есть папка канала,
а её путь относительно `_channels/` подставляется в `CHANNEL`. Значение
`PLAYLIST` чинится, если папка нашлась по последнему сегменту пути (частый
случай — в значение случайно попал контейнер: `IT\lectures` → `lectures`).

Абсолютный путь, ведущий не в корень проекта, переносится на новое место,
если цель определяется однозначно: сначала по самому длинному «хвосту»
пути, который существует внутри проекта, затем по имени папки — но только
если в проекте она такая одна. Иначе строка не трогается, а выводится
`WARNING` с просьбой поправить вручную. Строки с `%~dp0` и относительные
пути не трогаются: они переезд и так переживают.

Кодировка и переводы строк каждого файла сохраняются, так что кириллица в
`rem TITLE_SUBSTR=...` не страдает. Повторный запуск ничего не меняет.

## `read_chat_transcript.py`

Сервисный скрипт: делает читаемую копию расшифровки чата с агентом. Сама
расшифровка — это `.jsonl`, по одному JSON-объекту на строку, то есть целый
разговор на нескольких тысячах очень длинных строк, где переводы строк
внутри каждой команды, каждого файла и каждого ответа записаны как `\n`.
Лежит она в профиле пользователя:

```
%USERPROFILE%\.cursor\projects\<проект>\agent-transcripts\<id>\<id>.jsonl
```

### Запуск

```bat
python src\read_chat_transcript.py prompts\2026_07_30_Chat.jsonl
python src\read_chat_transcript.py prompts\2026_07_30_Chat.jsonl --split
python src\read_chat_transcript.py chat.jsonl --width 100 --out chat.txt
```

| Параметр | Значение |
|----------|----------|
| `--split` | Вместо одного текстового файла — папка с одним `.json` на сообщение (`0001_user.json`, …), каждый с отступом в два пробела. Остаётся валидным JSON |
| `--out` | Куда писать (по умолчанию — рядом с исходником: `<имя>.txt`, а с `--split` — папка `<имя>/`) |
| `--width` | Ширина текстовой копии (по умолчанию 80) |

### Как выглядит результат

Каждое сообщение — озаглавленный блок (`[17/2216] USER`), реплики
пользователя отбиты `=`, ответы агента `-`. Вызовы инструментов печатаются
как обычный JSON, со скобками. Строка, не влезающая в одну строку экрана,
выводится сырым текстом после метки — `|`, если в ней есть собственные
переводы строк (файл, скрипт), и `>`, если это одна длинная строка,
сложенная по ширине; метки взяты из YAML, где означают ровно это. После
такого блока запятая-разделитель не ставится: она читалась бы как часть
текста. Это копия для чтения, а не для разбора — для разбора есть исходный
`.jsonl` и режим `--split`.

Где рвать строку, решают удобства чтения, а не номер колонки, поэтому часть
строк выходит за 80 символов:

- разметка (обёртка `<timestamp>` / `<user_query>` вокруг реплики
  пользователя) раскладывается по одному тегу на строку с отступом по
  вложенности, а тег со слишком длинным списком атрибутов — по атрибуту на
  строку; текст между тегами режется по собственным переводам строк;
- команда складывается по конвейерам и точкам с запятой, стоящим снаружи
  кавычек: то, чем команда запускается, вместе с путём остаётся на первой
  строке, каждый следующий `|` открывает свою, а короткие звенья
  группируются, пока не наберётся около сотни символов — иначе выходит
  столбик огрызков;
- путь, URL и любое другое слово, внутри которого рвать нечего, остаётся
  целым, какой бы длины оно ни было.

Отсюда практическое следствие: длина самой длинной строки результата равна
длине самого длинного пути в нём. На чате из 2216 сообщений (96 тысяч строк)
за 80 символов выходят 1.8% строк, за 100 — 0.4%, и ни в одной из них не
остаётся пробела, за который можно было бы зацепиться.

## `find_youtube_channel_by_descr.py`

Шаг 0 пайплайна: поиск YouTube-канала по свободному текстовому описанию
(например, «Политолог Аббас Галлямов YouTube») и запуск для него шага 1.

### Запуск

```bat
_run_scripts\add_youtube_channel_by_descr.bat
python src\find_youtube_channel_by_descr.py "Политолог Аббас Галлямов YouTube"
```

В bat-файле редактируются две выделенные строки:

- `rem DESCR=...` — описание канала для поиска; первый параметр bat-файла,
  если задан, её переопределяет;
- `rem CHANNEL_PATH=...` — папка внутри `_channels\`, в которой создать
  папку канала (например, `IT\Dot.Net`); пустая строка означает сам
  `_channels\`. Второй параметр bat-файла её переопределяет; скрипту это
  уезжает как `--container`.

Обе строки — именно `rem`, а не `set "DESCR=..."`, по той же причине, что и
`rem TITLE_SUBSTR=...` в `transcribe_and_edit_next_by_substr.bat` (см. ниже):
cmd.exe читает bat в кодовой странице консоли и портит кириллицу по пути в
переменную, поэтому строку вычитывает из bat уже PowerShell как UTF-8.
Папка `_run_scripts/` в корне проекта и этот bat-файл входят в git.

Группа создаётся, если её ещё нет. Промежуточных папок может быть
несколько (`IT\Dot.Net\Core`), и они не обязаны существовать заранее. Путь,
ведущий за пределы `_channels\`, отвергается, а путь, указывающий на уже
существующую папку канала (в ней есть `_playlists\`), — тем более: канал
внутри канала не бывает.

Если папка этого канала уже где-то есть, она и используется — независимо от
`CHANNEL_PATH`, о чём выводится сообщение. Папка канала ищется по всему
дереву `_channels/` (по имени и по `channel_id` в `_cache`), так что
перенести её в другую группу можно вручную; после переноса — запустить
`_run_scripts\synchronize_folders_in_bats.bat`, который поправит пути,
зашитые в bat-файлах.

### Как работает

1. Поиск по YouTube с фильтром «каналы»; берутся до **трёх** лучших
   совпадений в убывающем порядке релевантности. Если по фильтру каналов
   ничего не нашлось (описание характеризует контент, а не название
   канала), выполняется обычный поиск видео и берутся каналы верхних
   результатов (в выводе помечаются строкой `Found via the video: ...`).
2. По каждому кандидату выводится: название, `@handle`, число подписчиков,
   описание, **общее число видео**, список **плейлистов с числом видео** в
   каждом. Названия плейлистов не на русском (и не транслитерация с
   русского) дополняются переводом на русский; тем же вызовом `gpt-4o`
   угадывается основной язык контента канала (без ключа API перевод
   пропускается). Если канал уже есть в `_channels/`, сообщается, есть ли
   у него summaries.
3. Для каждого кандидата по очереди запрашивается подтверждение
   (`y` — строить summary, `n` — следующий кандидат, `q` — выход). После
   `y` предлагается выбор группировки: по плейлистам (`bypls`) или плоским
   списком (`allpls`).
4. По подтверждению запускается `get_summary_for_channel` (создаёт и
   заполняет `_cache`, `_playlists`, `_summaries` в папке канала — внутри
   группы из `CHANNEL_PATH`, если она задана), досоздаётся `_run_scripts`,
   и в нём генерируются три bat-файла:
   - `transcribe_and_edit_next.bat` — транскрибировать + отредактировать
     очередное необработанное видео из **плоского списка всех видео
     канала**;
   - `transcribe_and_edit_next_by_substr.bat` — то же по всему каналу, но
     только для видео, в названии которых есть заданная подстрока
     (без учёта регистра и плейлистов). Подстрока задаётся редактируемой
     строкой `rem TITLE_SUBSTR=...` в шапке bat-файла; подходящих видео
     может быть несколько, и на каждое по очереди спрашивается
     подтверждение (`n` — перейти к следующему совпадению);
   - `transcribe_and_edit_next_bypl.bat` — то же для **одного плейлиста**:
     имя локальной папки плейлиста задаётся редактируемой строкой
     `set "PLAYLIST=..."` в шапке bat-файла (по умолчанию — плейлист с
     наибольшим числом видео по `_cache/video_playlists.json`). Перед
     следующим запуском строку можно сменить вручную.

Подстрока лежит именно в `rem`-строке, а не в `set "..."`, потому что
cmd.exe читает bat в кодовой странице консоли (cp437/cp866) и портит на
этом пути кириллицу; `rem`-строку cmd игнорирует, а её содержимое
вычитывает из bat уже PowerShell как UTF-8. Поэтому bat-файлы должны
сохраняться в UTF-8 без BOM.

Все три bat-файла вызывают `transcribe_videos.py --from-youtube --edit
--annotate --orig-only --next 1`: очередное — это очередное **не полностью
отредактированное** видео (уже оттранскрибированное, но неотредактированное
идёт сразу на редактирование); документы формируются только на языке
оригинала (язык прописан в шапке bat-файла из угаданного языка канала)
плюс аннотации 200–250 слов по правилам `--annotate`. Каждая стадия ждёт
своего подтверждения стоимости.

## `download_videos.py`

Шаг 2 пайплайна: скачивание видео канала утилитой `yt-dlp`. Скачивание
бесплатно — yt-dlp обращается к YouTube напрямую, без ключей и платных
сервисов; расходуются только диск и время.

### Запуск

```bat
python src\download_videos.py Game_Design\_makingitright9305 ^
    kurs_geym_dizayna_nri_making_it_right --next 1
python src\download_videos.py Game_Design\_makingitright9305 ^
    kurs_geym_dizayna_nri_making_it_right --next all
python src\download_videos.py _Autotesting --next all
```

**Параметр 1:** имя папки канала в `_channels/`.  
**Параметр 2:** имя папки плейлиста в `<канал>/_playlists/`. Если опущен,
берётся плоский список всех видео канала (новые сначала), и каждое видео
кладётся в папку своего плейлиста — как в плоском режиме
`transcribe_videos.py`; видео вне плейлистов идут в `misc/`.

| Параметр | Описание |
|----------|----------|
| `--next N` | Сколько видео скачать за сессию (default: 1); `--next all` — все недостающие |
| `--title-substr TEXT` | Только видео, в названии которых есть эта подстрока (без учёта регистра) |
| `--max-height PX` | Потолок высоты кадра (default: 1080); `0` — лучшее доступное качество |
| `--cookies-from-browser BROWSER` | Брать cookies YouTube из браузера (см. ниже про проверку «вы не робот») |
| `--cookies FILE` | Взять cookies из файла `cookies.txt` (формат Netscape); приоритетнее предыдущего |
| `--no-presentations` | Не искать под скачанным видео ссылку на презентацию (по умолчанию каждое скачанное видео проверяется; см. `download_presentations.py`) |
| `--yes` | Не спрашивать подтверждение (в том числе на загрузку найденной презентации) |

### Как работает

Список видео берётся оттуда же, откуда его берёт транскрибирование: для
плейлиста — из самого плейлиста YouTube (в порядке плейлиста), для плоского
режима — из `_cache/videos.json` плюс раскладка по папкам из
`_cache/video_playlists.json` и `_cache/playlists.json`.

Имя файла сразу пишется в конвенции проекта: `NN_<название> [<video id>].mp4`,
где `NN` — номер в плейлисте. Благодаря маркеру `[<video id>]` уже скачанное
видео распознаётся и пропускается, поэтому прерванный сеанс продолжается со
следующего запуска, а `--next 1` проходит плейлист за серию запусков. Длина
имени урезается под лимит пути так же, как в `transcribe_videos.py`.

Скачивается mp4 (при необходимости видео и звук сводятся `ffmpeg`).
Прогресс печатается раз в 5 секунд, чтобы не забивать лог. Клавиша `p`
останавливает сессию после текущего видео.

Сразу после скачивания видео читаются комментарии под ним: если лектор
выложил там презентацию, скрипт показывает найденную ссылку и предлагает
её загрузить (`y/n`) в папку `PRESENTATIONS/`. Отключается флагом
`--no-presentations`; подробности — в разделе `download_presentations.py`.

Автоматизация: `_channels/<канал>/_run_scripts/download_videos_all.bat`
(весь плейлист за один запуск) и `download_videos_next.bat` (по одному видео
за запуск). Плейлист, потолок качества и браузер для cookies задаются
переменными в шапке bat-файла.

### Требования и проверка «подтвердите, что вы не робот»

- `yt-dlp` (`pip install -U yt-dlp`) и `ffmpeg` в `PATH`;
- JavaScript-движок: начиная с версий 2026 года yt-dlp объявил извлечение
  форматов YouTube без него устаревшим и предупреждает, что часть форматов
  недоступна. Штатный вариант — Deno (`winget install DenoLand.Deno`),
  он подхватывается автоматически, настраивать ничего не нужно.

YouTube периодически отвечает `Sign in to confirm you're not a bot` — это
ограничение по IP, а не по формату: при нём одинаково отказывают все клиенты
плеера и даже загрузка одной аудиодорожки (то есть перестаёт работать и
`transcribe_videos.py --from-youtube`). Лечится передачей cookies
авторизованного браузера: `--cookies-from-browser firefox` (в bat-файлах —
переменная `COOKIES` в шапке). Браузер при этом должен быть полностью
закрыт, иначе он держит свою базу cookies заблокированной и yt-dlp отвечает
`Could not copy Chrome cookie database`. Получив такой отказ, скрипт
прекращает сессию сразу, не перебирая остальные видео: ограничение общее для
всех них. Если прочитать профиль не удаётся
(Chrome и Edge на свежих Windows дополнительно шифруют его), выручает
`--cookies cookies.txt` — файл в формате Netscape, выгруженный расширением
браузера.

## `download_presentations.py`

Шаг 2a пайплайна: презентация, которую лектор выложил в комментарии под
своим видео. Файл — это ровно то, что показано на экране в записи, поэтому
он ценен рядом с видео: с ним видно, каким слайдам обязаны соответствовать
извлечённые кадры, а окончательному документу есть на что опереться, кроме
распознавания текста с демонстрации экрана. Загрузка бесплатна — ни ключей,
ни платных сервисов.

Одному кадру презентации в записи обычно соответствует серия состояний с
последовательно наращиваемым содержанием — от одного заголовка до полного
кадра. Извлечение слайдов теперь берёт от такой страницы её последнее
состояние, а моменты появления пунктов записывает в `reveals.json`
(см. `extract_slides.py`), так что серия не теряется и не превращается в
десяток оплачиваемых кадров. Сами файлы презентаций пока просто лежат
рядом с видео; сверять их с извлечёнными кадрами — отдельная задача.

### Запуск

```bat
python src\download_presentations.py Game_Design\_makingitright9305 ^
    kurs_geym_dizayna_nri_making_it_right --next all
python src\download_presentations.py Game_Design\_makingitright9305 ^
    kurs_geym_dizayna_nri_making_it_right --video "04_Making It Right..."
```

| Параметр | Описание |
|----------|----------|
| `--next N` | Сколько видео просмотреть за сессию (default: 1); `all` — все, у которых презентации ещё нет |
| `--video STEM` | Только видео с этим именем файла (без расширения) |
| `--cookies-from-browser BROWSER`, `--cookies FILE` | Как в `download_videos.py`: нужны, когда YouTube просит подтвердить, что вы не робот |
| `--yes` | Загружать найденное без вопроса |

### Не «первый комментарий», а комментарий автора

Ссылка лежит в комментарии владельца канала, но это не обязательно первый
комментарий на странице: зрительские всплывают выше по числу лайков (в
лекции №4 курса Making It Right комментарий лектора — второй). Поэтому
поиск идёт по автору — среди комментариев автора видео, — а внутри них по
подписи перед ссылкой:

```
Презентация: https://drive.google.com/file/d/…/view?resourcekey=…
Схема рабочего процесса: https://drive.google.com/file/d/…
ТЗ на первый прототип: https://docs.google.com/document/d/…
```

Берётся ссылка, подписанная как «презентация» (или `slides` /
`presentation`); если лектор не подписал ничего — первая ссылка на документ
в его комментарии. Остальные материалы записываются в сайдкар, но не
скачиваются: этот шаг — про презентацию.

### Ключ ресурса: почему старая ссылка не открывается в браузере

Файлы, которыми поделились до 2021 года, Google с тех пор отдаёт только
вместе с `resourcekey` — ключом, который выдан вместе со ссылкой. Без него
и `drive.google.com/open?id=…`, и `uc?export=download` уводят на страницу
входа в аккаунт, отчего кажется, что материалы курса 2017 года потеряны.
Скрипт переносит ключ из ссылки в адрес загрузки, и файл скачивается без
всякого входа. Ссылки на редакторы Google (`docs.google.com/document/…`,
`/presentation/…`) выгружаются в PDF; прямые ссылки скачиваются как есть.

### Результаты

Для каждого видео — два файла в `<playlist>/PRESENTATIONS/`, названные по
имени видеофайла, как это принято для `INFO/<stem>.json`:

- `<stem>.pdf` (расширение — то, которое отдал сервер);
- `<stem>.json` — откуда файл взят: ссылка, подпись перед ней, автор
  комментария, исходное имя файла, размер, дата загрузки и список прочих
  материалов из того же комментария.

Загрузка идёт во временный файл и переименовывается в конце, поэтому
прерванная загрузка не выглядит на следующем запуске готовой.

### Откуда вызывается

- `download_videos.py` — сразу после скачивания видео (отключается
  `--no-presentations`);
- `extract_slides.py --presentations` — для видео, скачанных до появления
  этого шага; загрузка презентации предшествует извлечению слайдов.

Получив от YouTube отказ «подтвердите, что вы не робот», шаг прекращает
поиск и в остальных видео: ограничение общее для всех них.

Проверки (офлайн, на настоящих текстах комментариев курса):
`temp/_test_presentations.py`.

## `transcribe_videos.py`

Шаг 4 пайплайна: транскрибирование скачанных видео через OpenAI audio API
(`whisper-1`) — на языке оригинала и (для неанглийских) на английском.

### Запуск

```bat
python src\transcribe_videos.py _Autotesting lectures --lang ru
python src\transcribe_videos.py _Autotesting lectures --lang ru --next 3
python src\transcribe_videos.py AI_for_Game_Design\_makingitright9305 ^
    --lang ru --orig-only --from-youtube --edit --annotate ^
    --title-substr "Лекция №1.1." --next all
```

**Параметр 1:** имя папки канала в `_channels/` (в т.ч. «виртуального», как `_Autotesting`).  
**Параметр 2:** имя папки плейлиста в `<канал>/_playlists/`. В удалённом
режиме может быть опущен — тогда берётся **плоский список всех видео канала**
(см. ниже).

| Параметр | Описание |
|----------|----------|
| `--lang XX` | Язык оригинала, двухбуквенный код (default: `ru`) |
| `--next N` | Сколько видео транскрибировать за сессию (default: 1); `--next all` — все подходящие |
| `--title-substr TEXT` | Только удалённый режим: оставить видео, в названии которых есть эта подстрока (без учёта регистра). Каждое совпадение предлагается по очереди, и `n` переходит к следующему, а не завершает сессию |
| `--orig-only` | Только язык оригинала (пропустить английский проход) |
| `--from-youtube` | Брать очередное видео прямо с YouTube (см. ниже) |
| `--url URL` | Транскрибировать конкретное видео по его URL (удалённый режим) |
| `--slides` | Сразу после транскрибирования запустить `extract_slides.py` и `text_from_slides.py` для каждого видео сессии — чтобы следующий за ними `--edit` строил документ по слайдам. Читает кадры видеофайла, поэтому в удалённом режиме без скачанного видео флаг отклоняется |
| `--edit` | Сразу после транскрибирования (и после слайдов, если задан `--slides`) запустить `create_final_docs.py`. Без `--slides` этапы слайдов пропускаются, и оглавление строится по таймкодам видео (см. `--no-slides` там). В удалённом режиме «очередное» видео — очередное **неотредактированное**: уже оттранскрибированное, но не отредактированное видео пропускает транскрибирование и идёт сразу на редактирование |
| `--annotate` | Вместе с `--edit`: создавать и аннотацию 200–250 слов (см. `create_final_docs.py`) |
| `--terms FILE` | Глоссарий курса, передаваемый распознавателю (default: `terms.txt` папки плейлиста, затем папки канала) |
| `--yes` | Не спрашивать подтверждение на каждое видео |
| `--ffmpeg`, `--ffprobe` | Пути к исполняемым файлам (default: из `PATH`) |

Перед транскрибированием каждого видео скрипт выводит длительность и оценку
стоимости и ждёт подтверждения `y/n` (ответ `n` завершает сессию, а с
`--title-substr` — переходит к следующему совпадению).
Флаг `--yes` отключает вопрос (для запусков без присмотра).

### Докуда доходит пайплайн: `--slides` и `--edit`

Два флага независимы, и вместе они покрывают все четыре случая:

| Флаги | Что происходит после транскрибирования |
|-------|----------------------------------------|
| — | ничего: остаются транскрипты |
| `--slides` | извлекаются слайды и их текст; остановка перед редактированием, `slides.json` готов к отдельному запуску `create_final_docs.py` |
| `--edit` | сразу редактирование, этапы слайдов пропущены: оглавление строится по таймкодам видео |
| `--slides --edit` | весь пайплайн до конца — слайды, текст слайдов, документы по слайдам |

Каждое видео сессии проходит эти этапы поимённо: `extract_slides.py --video
<stem>`, затем `text_from_slides.py --video <stem>`. Все платные этапы —
транскрибирование, чтение слайдов, редактирование — показывают свою оценку
стоимости и спрашивают подтверждение отдельно; `--yes` отвечает за все
(извлечение слайдов бесплатно и ни о чём не спрашивает).

`--slides` относится только к видео **этой сессии** — к тем, что сейчас
транскрибированы (в удалённом режиме с `--edit` — и к тем, что взяты сразу
на редактирование). Уже готовые видео флаг не подхватывает: для них
слайдовые шаги запускаются своими скриптами.

Слайды извлекаются из кадров видеофайла, а удалённый режим скачивает только
аудиодорожку. Поэтому `--from-youtube --slides` без единого видеофайла в
папке плейлиста отклоняется сразу — до трат на транскрибирование — с
предложением скачать видео (`download_videos.py`). Если файлы есть, но
конкретного видео среди них нет (плоский режим канала), слайдовые шаги для
него пропускаются с предупреждением, а редактирование идёт своим чередом.

### Удалённый режим (`--from-youtube` / `--url`)

Видео не обязано быть скачано. Скрипт находит YouTube-плейлист, соответствующий
локальной папке плейлиста, через `_cache/playlists.json` (его строит скрипт
summary), берёт **очередное** нетранскрибированное видео в порядке плейлиста
(или конкретное видео из `--url`) и:

- скачивает во временную папку только аудиодорожку (yt-dlp, `bestaudio`);
  если видео уже скачано локально (по `[id]` в имени файла) — используется
  локальный файл без скачивания;
- сохраняет метаданные видео (название, дата, длительность, таймкоды/chapters)
  в `<playlist>/INFO/<stem>.json` — они нужны финальному редактированию
  (заголовок документа и оглавление по таймкодам);
- имена результатов — в локальной конвенции: `NN_<название> [<id>]`,
  где `NN` — номер в плейлисте.

Windows по умолчанию не разрешает пути длиннее 260 символов, а самый длинный
файл, который строится от `<stem>`, — это `<playlist>/<LANG>/OUTPUT/<stem>.docx`.
Поэтому название в `<stem>` при необходимости обрезается так, чтобы уложиться;
номер `NN_` и маркер `[<id>]` сохраняются всегда — по `[<id>]` скрипты и
находят уже готовые файлы. В логе это видно строкой `Long path: the file name
was shortened to N characters`. Если даже обрезка не помогает (очень глубокая
вложенность папок канала), выводится предупреждение с советом перенести канал
ближе к корню диска.

Действующий лимит скрипт определяет сам: он читает `LongPathsEnabled` в
`HKLM\SYSTEM\CurrentControlSet\Control\FileSystem` и, если длинные пути в
системе включены, поднимает потолок с 260 до 400 символов — этого с запасом
хватает на любой заголовок YouTube (там максимум 100 символов), так что
обрезка фактически перестаёт срабатывать. Именно 400, а не системные 32 767,
потому что готовый `.docx` дальше открывается внешним WPS Writer или Word для
экспорта в PDF, а они длинные пути поддерживают не гарантированно.

Включить длинные пути в системе (PowerShell от администратора, требуется
перезапуск программ, но не всей Windows):

```powershell
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem" `
  -Name LongPathsEnabled -Value 1 -Type DWord
```

**Плоский режим (папка плейлиста опущена):** список видео берётся из
`_cache/videos.json` (его строит скрипт summary), в порядке ленты канала
(новые сверху). Каждое видео обрабатывается в **своей** папке плейлиста
(карта `_cache/video_playlists.json`); видео вне плейлистов — в папке
`misc/`.

С `--edit` после транскрибирования для каждого видео автоматически
вызывается `create_final_docs.py --no-slides --video <stem>` (плюс
`--orig-only` / `--annotate`, если заданы); стадия редактирования
показывает свою оценку стоимости и ждёт отдельного подтверждения `y/n`.
Видео, уже оттранскрибированные, но ещё не отредактированные, пропускают
транскрибирование (без затрат) и идут сразу на редактирование.

Флаг `--slides` здесь работает только для скачанных видео: с YouTube
приходит одна аудиодорожка, а слайды нарезаются из кадров.

### Глоссарий курса (`terms.txt`)

Английские названия в русской речи распознаются хуже всего: «Playwright» в
этом курсе стал «PlevRite», «Pleuride» и «плеврайтом», а CI/CD — «OCD».
Лечится это бесплатно: у audio API есть поле `prompt`, которое читается как
текст, предшествующий записи, и смещает распознавание к нужному написанию.

Файл `terms.txt` (по одному термину в строке, `#` — комментарий) кладётся
в папку плейлиста — или в папку канала, если он общий для всех плейлистов;
`--terms` указывает на любой другой. Термины уходят распознавателю обоих
проходов. Лимит поля — 224 токена, лишние термины отбрасываются с
сообщением в логе, так что список стоит держать коротким.

Материал для такого списка даёт `check_transcripts.py` — его частотные
разделы показывают, какие термины курс произносит чаще всего и как именно
их коверкает распознавание.

### Результаты

Для каждого видео `<stem>.<ext>` создаются `<stem>.txt` (текст абзацами:
абзацы разделены пустой строкой — границы по настоящим паузам записи, см.
`silences.py`; строки до 80 символов без переносов в словах) и `<stem>.srt`
(субтитры с таймкодами) в подпапках плейлиста:

- `<playlist>/<LANG>/` — язык оригинала (имя папки — код языка в UpperCase: `RU`, `EN`);
- `<playlist>/EN/` — английский перевод (второй аудиопроход, endpoint `translations`),
  только если язык оригинала — не английский.

Рядом с ними сохраняется `<stem>.asr.json` — то, что API сообщает о качестве
собственной работы: для каждого сегмента `avg_logprob` (насколько уверенно он
его расслышал), `no_speech_prob` и `compression_ratio`. Эти данные приходят в
том же ответе и раньше просто отбрасывались; их использует проверка
транскриптов. Файл — sidecar, а не часть комплекта результатов: транскрипты,
сделанные до его появления, по-прежнему считаются полными и не будут
переделаны.

### Порядок и возобновление

Видео обрабатываются в порядке сортировки по имени файла. Стартовая точка
сессии определяется сканированием папок результатов: первое видео без полного
комплекта файлов. Отдельный флаг `--resume` не нужен — каждый запуск
продолжает с места остановки. Клавиша `p` во время сессии — мягкая пауза:
скрипт остановится после текущего видео.

### Требования

- `ffmpeg` / `ffprobe` в `PATH` (аудио извлекается в mp3 16 кГц моно и режется
  на куски ≤24 мин под лимит API 25 МБ/запрос);
- ключ API в переменной окружения `OPENAI_API_KEY` или в `.env` в корне проекта:

```text
OPENAI_API_KEY=sk-...
```

Тариф ($0.006/мин за проход) берётся из общего кэша `_cache/transcription_pricing.json`
(см. раздел про оценку стоимости выше). Оценка стоимости сессии выводится в консоль.

## `silences.py`

Шаг 4b пайплайна, необязательный: где лектор замолкал. Работает офлайн
(нужен только `ffmpeg`), API не трогает и потому ничего не стоит.

Паузы нужны абзацам. В `.srt` их нет: whisper подгоняет тайминги встык,
и пауза между двумя предложениями на бумаге равна нулю, какой бы она ни
была в аудитории. В самой записи они, разумеется, есть — 350–730 на
лекцию, 5–11 минут тишины из часа с небольшим.

### Запуск

```bat
python src\silences.py _Autotesting lectures
python src\silences.py _Autotesting lectures --refresh
```

| Параметр | Назначение |
|----------|------------|
| `--refresh` | снять заново, даже если сайдкар уже есть |
| `--ffmpeg` | путь к `ffmpeg` (по умолчанию — из `PATH`) |

Отдельно запускать не обязательно: `create_final_docs.py` и
`transcribe_videos.py` снимают паузы сами, когда сайдкара ещё нет.

### Как это работает

`ffmpeg -af silencedetect=noise=-30dB:d=0.35` над одним только звуком
(`-vn`, видео не декодируется) — 2–3 секунды на часовую лекцию. Порог
−30 дБ оставляет за бортом дыхание и шум помещения, но ловит остановки
между фразами.

Результат кладётся рядом с видео: `01_Introduction.mp4` →
`01_Introduction.silences.json`. В сайдкаре записаны и настройки, с
которыми он снят, так что при их изменении он снимается заново, а не
используется молча. Если видео нет (удалённый режим) или `ffmpeg`
недоступен, паузы просто отсутствуют — абзацы тогда режутся по длине, как
раньше.

## `check_transcripts.py`

Шаг 4a пайплайна, необязательный: отчёт о подозрительных местах транскрипта.
Работает офлайн, обращений к API не делает и потому ничего не стоит.

### Запуск

```bat
python src\check_transcripts.py IT\_Autotesting lectures
python src\check_transcripts.py IT\_Autotesting lectures --video 01_Introduction
```

| Параметр | Описание |
|----------|----------|
| `--lang XX` | Язык оригинала, двухбуквенный код (default: `ru`) |
| `--video STEM` | Проверить только один транскрипт (default: все в папке) |
| `--terms FILE` | Глоссарий курса; его термины считаются известными словами |
| `--rare-count N` | Незнакомое слово, сказанное в плейлисте больше N раз, — лексикон лектора, а не ошибка (default: 2) |
| `--min-logprob X` | Порог уверенности распознавателя (default: −0.45; нужен `.asr.json`) |
| `--max-no-speech X` | Порог вероятности «это вообще не речь» (default: 0.5) |

### Три сигнала

Ошибки распознавания распределены по лекции не равномерно: они собираются на
англоязычных терминах, именах и на местах, где лектора было плохо слышно.
Указывают на них три бесплатных признака:

- **слово вне морфологического словаря** (pymorphy3) — «засанить», «хотки»:
  либо намеренное заимствование, либо, чаще, ослышка;
- **латинское слово, которого нет в английском транскрипте** того же видео —
  «PlevRite» против «Playwright»: так это слово не пишет больше никто.
  Английский транскрипт здесь работает камертоном, и стоит это ноль токенов;
- **уверенность самого распознавателя** (`avg_logprob` из `.asr.json`) —
  она отделяет «редкое слово» от «слова, которое он еле расслышал».

Чтобы отчёт не тонул в шуме, частотные слова из него убираются: ослышка —
явление разовое, а слово, которое лектор повторяет из лекции в лекцию
(«тестировщик», «поинты»), — это его лексикон, которого просто нет в словаре.
Частота считается по нормальной форме и по **всем** транскриптам плейлиста,
даже когда проверяется один: одной лекции мало, чтобы отличить привычку от
оговорки.

Слова, смешивающие алфавиты («environment-ах», «performance-тестирование»),
выносятся отдельным списком. Это не ошибки, а решения транскрипта о том, как
записывать заимствования, и увидеть их разом — единственный способ привести
их к общей политике.

### Результаты

Отчёт по каждому видео — в `<playlist>/<LANG>/CHECKS/<stem>.txt`: сначала
сводка, затем подозрительные сегменты с таймкодом, уверенностью и пометками,
затем три частотных списка. Списки — готовый материал для `terms.txt`.

На этом курсе (10 лекций, 6 секунд работы) проверка нашла, например,
`Playwright` в написаниях `PlevRite`, `Pleuride`, `Plowrite`, `Plevirate` и
«плеврайт», регулярки `\d`/`\w`/`\s` как `SlashD`/`SlashW`/`SlashS`, CI/CD как
`OCD` и `ICD`, mocks как `MOKI`, а assertions — как «осершинов».

### Требования

`pymorphy3` (`pip install -r src/requirements.txt`) — только для языков с
морфологическим словарём (`ru`, `uk`). Без него и для остальных языков
проверка работает, но без разбора незнакомых слов: остаются латиница и
уверенность распознавания.

## `extract_slides.py`

Шаг 5 пайплайна: извлечение слайдов из видео-презентаций (редко сменяющиеся
слайды). Детекция смены сцены — PySceneDetect (`pip install scenedetect[opencv]`),
работает локально и бесплатно.

### Запуск

```bat
python src\extract_slides.py _Autotesting lectures
python src\extract_slides.py _Autotesting lectures --next 3 --threshold 20
python src\extract_slides.py _Autotesting lectures --video 01_Introduction
```

Параметры 1 и 2 — как у `transcribe_videos.py` (папка канала, папка плейлиста).

| Параметр | Описание |
|----------|----------|
| `--next N` | Сколько видео обработать за сессию (default: 1) |
| `--video STEM` | Только видео с этим именем файла (без расширения); так этот шаг вызывает цепочка `transcribe_videos.py --slides`. Короткие ключи папок `SLIDES/` при этом считаются по всему плейлисту, а не по выбранному видео |
| `--threshold T` | Чувствительность детекции; меньше = чувствительнее (default: 20) |
| `--min-scene-seconds S` | Минимальная длительность слайда, сек (default: 4) |
| `--crop-margin F` | Доля кадра, отрезаемая с каждого края перед детекцией, чтобы статичная рамка (интерфейс браузера, панель участников, часы) не размывала реальные смены слайдов; 0 отключает (default: 0.15) |
| `--start-offset S` | Через сколько секунд после начала сцены снимается ранний кадр — тот, с которым сравнивается последнее состояние страницы, и тот, что сохраняется при `--first-frame` (default: 1.0) |
| `--no-merge` | Не сливать почти одинаковые соседние сцены |
| `--first-frame` | Сохранять кадр начала сцены, а не последнее состояние страницы (прежнее поведение) |
| `--no-reveals` | Не искать моменты появления содержания внутри сцены и не писать `reveals.json` |
| `--image-format png\|jpg\|webp` | Формат изображений (default: png) |
| `--presentations` | Перед извлечением слайдов поискать под видео презентацию, выложенную лектором в комментарии, и предложить её загрузить (см. `download_presentations.py`) |
| `--cookies-from-browser BROWSER`, `--cookies FILE` | Только с `--presentations`: cookies для YouTube |
| `--yes` | Только с `--presentations`: загружать найденное без вопроса (само извлечение слайдов ничего не спрашивает) |

С флагом `--presentations` перед слайдами каждого видео выполняется шаг 2a:
поиск и загрузка презентации. Сам `download_videos.py` спрашивает про
презентацию при скачивании, так что флаг нужен для видео, скачанных до
появления этого шага, — и он не включён по умолчанию, потому что дорога от
локального файла к странице видео и её комментариям неблизкая.

### Как детектируются слайды

- Смена сцены ищется только по **центральной части кадра** (`--crop-margin`):
  на записях демонстрации экрана статичное окружение (браузер, миниатюры,
  список участников) иначе «разбавляет» метрику изменения, и тонкие смены
  слайдов теряются. Благодаря обрезке порог по умолчанию снижен до 20.
- Кадр слайда — это **последнее состояние страницы**: кадр незадолго до
  конца сцены. Страница, пункты которой появляются по одному, остаётся
  одной сценой (одна строка — слишком малое изменение, чтобы её завершить),
  поэтому её первый кадр — обычно голый заголовок. Измерено на лекции 1
  курса Making It Right: в коллекцию попадал заголовок «Почему не надо
  делать игры?» без единого пункта, тогда как через две минуты на той же
  странице стояли шесть пунктов, цитата и картинка. Если поздний кадр
  потерял то, что было на раннем (лектор переключил окно, не дождавшись
  конца сцены), сохраняется ранний. Прежнее поведение — `--first-frame`.
- Соседние сцены с почти одинаковым содержимым центральной области
  (переключения окон, скролл, всплывающие панели) **сливаются в одну сцену**
  с одним изображением. Случай «тот же слайд, развёрнутый на весь экран»
  распознаётся сопоставлением ключевых точек (ORB) с учётом масштаба.
  Появление новой строки текста на слайде сливанием не считается — такие
  сцены сохраняются отдельно. Отключается флагом `--no-merge`.

### Моменты появления содержания: `reveals.json`

Внутри одной сцены содержание страницы может нарастать: пункты выходят по
одному, к ним добавляется картинка. Детектор сцен этого не видит, а знать
это полезно — момент появления пункта и есть момент, когда лектор о нём
заговорил. Поэтому каждая сцена просматривается ещё раз, кадр в две
секунды, и сравнивается по карте краёв с последним принятым состоянием:

- краёв **прибавилось, прежние на месте** (сохранилось ≥ 75%) — страница
  выросла, это `"kind": "added"`;
- **прежних краёв не осталось** — содержание заменили, это
  `"kind": "replaced"`; отдельным слайдом такое состояние пока не
  становится, но записывается — чтобы потом было на чём решать, стоит ли;
- беспокойные пиксели (окно вебкамеры лектора) в сравнении не участвуют:
  они находятся по нескольким десяткам пар кадров, снятых с промежутком в
  полсекунды — говорящая голова меняется почти в каждой паре, слайд не
  меняется ни в одной.

Записывается время, доля добавленного, доля сохранившегося и полоса по
вертикали, в которой появилось новое (по основной массе новых краёв, без
крайних 5% — отдельные шумовые точки на фотографии иначе растягивают
полосу на всю страницу). Просмотр бесплатный: ни одного обращения к
платным сервисам, только ещё один проход по видеофайлу (порядка минуты на
десять минут записи). Отключается флагом `--no-reveals`.

`text_from_slides.py` переносит эти записи в `slides.json` — в описание
того самого слайда, картинка которого показывает последнее состояние
страницы. В платный запрос к модели они не попадают, так что чтение
слайдов не дорожает.

### Результаты

Для каждого видео — папка `<playlist>/SLIDES/<short-key>/`:

- `slide_001.png`, `slide_002.png`, … — по одному кадру на сцену: последнее
  состояние её страницы;
- `reveals.json` — по сцене: моменты, когда на странице появлялось новое
  содержание (см. выше);
- `scenes.csv` — номера сцен и таймкоды начала/конца — удобно сопоставлять
  слайды с таймкодами транскрипции из `.srt`; после стандартных столбцов,
  через один пустой, — вычисленная частота кадров `Frame Rate (fps)`;
- `scenes.xlsx` — те же данные для Excel: таймкоды записаны как настоящие
  длительности с форматом `[ч]:мм:сс.000`, поэтому «1:01:47 от начала»
  отображается корректно (CSV не умеет передавать форматы ячеек, и Excel
  показывает такие значения как время суток, обрезая часы).

`<short-key>` — кратчайший префикс имени видеофайла (без расширения),
однозначно отличающий это видео от остальных в плейлисте (часто просто
ведущий номер: `01`, `02`, …). Короткие имена нужны, чтобы пути к
`scenes.csv` не упирались в лимит Windows MAX_PATH.

Порядок и возобновление — как у `transcribe_videos.py`: сортировка по имени
файла, готовность определяется наличием непустой папки `SLIDES/<short-key>/`
(изображения пишутся во временную папку и переименовываются по завершении,
прерванное видео переделывается при следующем запуске). Если смен слайдов
не найдено, сохраняется один кадр всего видео.

Переименовать уже созданные папки со старыми полными именами:

```bat
python src\extract_slides.py _Autotesting lectures --rename-existing
```

## `text_from_slides.py`

Шаг 6 пайплайна: извлечение текста из слайдов, полученных `extract_slides.py`,
в файл `slides.json` — с прицелом на формирование оглавления (ToC) будущего
отредактированного транскрипта. Использует OpenAI API (модель `gpt-4o`),
ключ — тот же, что у `transcribe_videos.py` (`OPENAI_API_KEY` / `.env`).

### Запуск

```bat
python src\text_from_slides.py _Autotesting lectures
python src\text_from_slides.py _Autotesting lectures --next 3
python src\text_from_slides.py _Autotesting lectures --video 01_Introduction
```

Параметры 1 и 2 — как у предыдущих скриптов (папка канала, папка плейлиста).
`--next N` — сколько видео обработать за сессию (default: 1). Видео попадает
в сессию, если для него есть папка `SLIDES/<short-key>/` со слайдами, но в ней
ещё нет `slides.json`; берутся первые N таких видео по порядку имён файлов.
`--video STEM` выбирает одно видео по имени — так этот шаг вызывает цепочка
`transcribe_videos.py --slides`.

### Сколько это стоит

Перед чтением слайдов очередного видео скрипт печатает оценку и ждёт
подтверждения `y/n` — как и остальные платные шаги; `--yes` отвечает за все
(и передаётся сюда из `transcribe_videos.py --slides --yes`).

Оценка запроса считается арифметикой, а не догадкой: кадр с `detail: high`
стоит ровно столько, сколько говорит его размер. Изображение вписывается в
квадрат 2048, затем короткая сторона приводится к 768, и каждая плитка
512×512 результата тарифицируется в 170 токенов плюс 85 базовых. Демонстрация
экрана 1920×1080 превращается в 1366×768 — шесть плиток, 1105 токенов на
слайд. Размер кадра читается из заголовка файла (PNG, JPEG, WebP), без
графических библиотек.

Ответы модели заранее не известны, поэтому они взяты по средним курса:
~650 токенов на лекцию плюс ~150 на слайд. На девяти лекциях курса
тест-автоматизации, где расход записан в логах, оценка запроса сходится с
фактическим счётом в пределах нескольких процентов, а полная стоимость —
в пределах четверти. Практика: $0.02–0.20 за лекцию.

Проверки — `temp/_test_slides_estimate.py`; посмотреть оценку по всем уже
извлечённым слайдам, ничего не тратя, — `temp/_slides_estimate_probe.py`.

### Как это работает

Два прохода через API:

1. **Распознавание** — по одному vision-запросу на каждый `slide_NNN.png`.
   Кадр может показывать слайд внутри интерфейса приложения (PowerPoint,
   браузер, Microsoft Teams с панелью участников) — читается только
   центральный прямоугольник с демонстрируемым контентом. Внутри слайда
   разделяются заголовок (самый заметный текст, в т.ч. крупный текст слева)
   и обычный текст (пункты по порядку). Текст извлекается дословно, без
   исправлений и перевода; фотографии (например, лектора) помечаются.

2. **Анализ структуры** — один запрос по всей последовательности слайдов.
   Распознаётся паттерн «лекция в составе курса лекций»:

   - слайд с общей информацией о записи (дата, кто записал) → метаданные
     документа, на английском;
   - вводные слайды о лекторе и о курсе → ненумерованные разделы перед
     основной частью;
   - слайд только с темой лекции → заголовок документа: номер из имени
     файла + тема (`01_Introduction.mp4` + «Introduction to Test
     Automation» → «01. Introduction to Test Automation»);
   - слайд Agenda → нумерованное оглавление всей лекции (финальный пункт
     Q&A — маркер, что список покрывает основную часть целиком);
   - последующие слайды сопоставляются с пунктами Agenda; если заголовок
     слайда — более полная формулировка короткого пункта, в ToC идёт
     заголовок слайда;
   - слайд, не заявленный в Agenda, вставляется в ToC на своём месте
     с флагом `needs_confirmation`;
   - финальные слайды с малым временем показа (Q&A, «спасибо», фото) —
     роль `closing`, отдельных разделов не образуют.

   Придумывание и правка заголовков — не задача этого шага: где заголовок
   пришлось изобрести (фото вместо заголовка) — флаг `title_invented`, где
   он неудачен — `title_needs_editing`; окончательные решения принимает
   следующий шаг пайплайна (финальное редактирование).

### Результат: `slides.json`

В папке `SLIDES/<short-key>/` рядом со слайдами:

- `document` — заголовок документа, метаданные (`date`, `recorded_by`,
  `language`) и оглавление `toc` (номер, название, слайд-источник, флаги);
- `slides` — по записи на слайд: имя файла, таймкоды сцены из `scenes.csv`,
  моменты появления содержания из `reveals.json` (поле `reveals`), тип
  содержимого (`text` / `photo` / `photo_and_text` / `empty`), заголовок,
  обычный текст (список строк), описание фотографии, роль (`lecture_info`,
  `foreword`, `lecture_title`, `agenda`, `section`, `content`, `closing`,
  `photo`), привязка к разделу ToC, флаги и заметки.

Картинка слайда — последнее состояние его страницы, поэтому текст в записи
полный, а `reveals` говорит, когда каждая его часть появилась на экране:
пункты выходят сверху вниз, и порядок моментов совпадает с порядком строк
в `body`. Модели этот список пока не показывается — он записан для шага
финального редактирования, где привязка подразделов к пунктам слайда
сейчас угадывается по ключевым словам транскрипта.

Автоматизация: `_channels/<канал>/_run_scripts/text_from_slides.bat`
(по образцу `extract_slides.bat`, лог — в `_run_scripts/_logs/`).

## `create_final_docs.py`

Шаг 7 пайплайна — финальный: из транскриптов и `slides.json` формируются
отредактированные версии документов. Используется OpenAI API (`gpt-4o`),

### Запуск

```bat
python src\create_final_docs.py _Autotesting lectures
python src\create_final_docs.py _Autotesting lectures --next 3
```

Параметры 1 и 2 — как у предыдущих скриптов. Видео попадает в сессию, если

| Параметр | Описание |
|----------|----------|
| `--next N` | Сколько видео обработать за сессию (default: 1) |
| `--doc DOCX` | Файл .docx — образец стилей для создаваемого .docx (default: встроенные стили по образцу `Docs_Edited/01_Introduction.V2.docx`: заголовок документа — heading 2, разделы — heading 3, подразделы — heading 4, дословный текст слайдов — `ds-markdown-paragraph`) |
| `--pdf DOCX` | Отдельный шаблон стилей только для PDF-версии (default: PDF печатается из создаваемого .docx) |
| `--orig-only` | Формировать `OUTPUT` только для языка оригинала (без английской версии) |
| `--no-slides` | Обрабатывать и видео без `slides.json`: заголовок документа строится в формате summary (`<канал> \| <плейлист> : <название>`), оглавление — по таймкодам видео из `INFO/<stem>.json` (его сохраняет `transcribe_videos.py` в удалённом режиме); видео со `slides.json` по-прежнему используют слайды |
| `--annotate` | Дополнительно создавать аннотацию 200–250 слов в `.txt` (см. ниже) |
| `--video STEM` | Обработать только видео с этим именем файла (без расширения); используется цепочкой `transcribe_videos.py --edit` |
| `--force` | Пересоздать документы и для видео, у которых `OUTPUT` уже готов (кэш редактирования при этом переиспользуется — заново редактируются только разделы, не прошедшие контроль полноты) |
| `--terms FILE` | Глоссарий курса, по которому редактор пишет термины (default: `terms.txt` папки плейлиста, затем папки канала) |
| `--yes` | Не задавать вопрос-подтверждение стоимости перед каждым видео |

Без `slides.json` и без таймкодов документ состоит из одного раздела
(«Транскрипт»); кэш редактирования в этом режиме — `INFO/<stem>.edited_sections.json`.

Заголовок раздела в этом режиме — название главы, если её назвал автор
видео: это его собственный заголовок, и он ставится дословно на всех
языках. Но главы бывают и автоматические, сделанные самим YouTube: они
приходят либо как `<Untitled Chapter 1>`, либо строчной строкой из речи
(`create a new dotnet core console`) — оглавление из таких строк читать
нельзя. Автоматические главы распознаются по всему набору сразу (YouTube
именует либо все, либо ни одной) и уступают место заголовку, который
редактор всё равно пишет для каждого раздела: `Introduction to Reflections
in .NET Core`. Ключ кэша при этом не меняется — уже отредактированные
разделы переизданию не подлежат.

### Термины и заимствования

Редактор получает тот же `terms.txt`, что и распознаватель (см. раздел
«Глоссарий курса» выше), — список уходит в каждый запрос: и в редактирование
раздела, и в точечную починку фрагмента, и в аннотацию. Термины из списка
пишутся ровно так, как в нём записаны, и по ним же чинится то, что сделало
с ними распознавание («PlevRite», «Pleuride», «плеврайт» → `Playwright`).
Глоссарий из 54 терминов добавляет ~135 токенов к разделу — около $0.004 на
часовую лекцию; в оценку стоимости это заложено.

Заимствования в русской морфологии («зарелизиться», «зафейлились») — это
речь лектора, а не ошибки, и они сохраняются. Правило записи такое:
устоявшаяся калька пишется так, как её уже пишет язык («деплой»,
«фреймворк»); латинская основа остаётся латинской, а окончание
присоединяется через дефис («environment-ах», «benefit-ы»); словосочетание,
сохраняющее английскую грамматику, остаётся английским целиком (`course
description`); термин, стоящий на слайде, пишется как на слайде. Один и тот
же термин пишется одинаково по всему документу.

Изменение глоссария или правил не сбрасывает кэш редактирования: уже
отредактированные разделы останутся как есть, пока их не переиздать
(`--force` пересоздаёт только документы; для повторного редактирования
нужно удалить `edited_sections.json` — по нынешним ценам это ~$0.45 за
двенадцатираздельную лекцию).

### Аннотации (`--annotate`)

Для каждого видео дополнительно генерируется аннотация в 200–250 слов
(отдельный вызов `gpt-4o`; результат кэшируется в том же кэше редактирования,
ключ `__annotation__`):

- язык оригинала **русский** → одна аннотация на русском:
  `RU/OUTPUT/<имя>.txt`;
- язык оригинала **не русский** → аннотация на английском
  (`EN/OUTPUT/<имя>.txt`) и её перевод на русский (`RU/OUTPUT/<имя>.txt`);
  сами документы (`md`/`docx`/`pdf`) при этом формируются только на языке
  оригинала (`--orig-only`), т.е. для языка, отличного от русского и
  английского, в папках `EN/OUTPUT` и `RU/OUTPUT` лежат только короткие
  аннотации.

Формат `.txt`: заголовок — тот же, что в отредактированных документах, затем
текст в правилах `.md`-файлов (строки ровно 80 символов с выравниванием
пробелами, без переносов в словах, абзацы через пустую строку). Если черновик
аннотации короче 200 слов, скрипт делает один уточняющий вызов «расширить до
200–250 слов». Промпт аннотации ограничен ~18k токенов (лимит TPM
организации): для длинных видео берутся заголовки разделов и
пропорциональные начала разделов.

### Стоимость и подтверждение

Затраты — это вызовы OpenAI API (`gpt-4o`): по одному вызову на раздел
документа. Перед началом редактирования скрипт печатает оценку (число
токенов и стоимость в долларах по тарифам `gpt-4o`: $2.50 за 1M токенов
запроса, $10.00 за 1M токенов ответа) и ждёт подтверждения `y/n` — как
`transcribe_videos.py`. Оценка считается по размеру фрагментов транскриптов
(~2.5 символа на токен для русского, ~4 — для английского) плюс накладные
токены на раздел.

Результаты редактирования кэшируются в `SLIDES/<short-key>/edited_sections.json`
после каждого раздела. Если запуск оборвался (например, на этапе PDF) или
нужно только переделать форматирование, повторный запуск возьмёт готовые
разделы из кэша и API-вызовов почти не будет (оценка покажет ~$0.00). Чтобы
принудительно отредактировать заново — удалите этот файл.

Исключение — разделы, не прошедшие контроль полноты (см. ниже): они
редактируются заново и показываются в оценке отдельной строкой.

### Как строится документ

- Список разделов с интервалами времени берётся из `slides.json`:
  инфослайд открывает Foreword, вводные слайды — ненумерованные разделы,
  слайд Agenda — раздел Agenda, слайды пунктов Agenda — нумерованные
  разделы, финальные слайды объединяются в «Заключение» / Conclusion.
- Граница между разделами сдвигается с середины фразы к ближайшему концу
  предложения (см. ниже).
- `.srt`-транскрипты нарезаются по этим интервалам: каждый раздел получает
  свой фрагмент оригинала и английского перевода, уже разбитый на абзацы
  по паузам самой записи (см. ниже).
- Каждый раздел редактируется через API с обоими фрагментами сразу:
  ошибки распознавания оригинала исправляются по английскому переводу
  (особенно искажённые англоязычные названия; там, где два распознавания
  расходятся, английское нередко сохраняет то, что русское потеряло —
  проглоченную придаточную часть или самопоправку лектора), пунктуация
  обогащается
  (двоеточия, тире — а не только запятые), текст разбивается на абзацы и
  минимально «причёсывается» с сохранением всего содержания; термины
  пишутся по глоссарию курса (см. ниже), а неудачные англоязычные
  формулировки в заголовках правятся.
- Подразделы — общий случай двух предельных вариантов: если текст раздела
  последовательно проходит по пунктам слайда (как «Benefits of Test
  Automation»), создаётся по подразделу на каждый пункт; если пункты лишь
  упомянуты вскользь и текст не распадается (как «What Is Test
  Automation?»), раздел остаётся сплошным. Частичное разбиение запрещено.
  Пояснительные слайды (строки вида `Definition: … Purpose: … Example: …`)
  принудительно остаются сплошными, раздел Agenda — тоже.

### Границы разделов: не по слайду, а по концу предложения

Слайд переключают рукой, посреди речи, поэтому момент его смены — плохое
место для разреза текста. На курсе по автотестированию из 103 границ
разделов **48 приходились на середину предложения**: половина фразы
оставалась в предыдущем разделе, половина открывала следующий. Отсюда же
и дубли между соседними разделами — редактор, получив кусок, начинающийся
с середины мысли, восстанавливает контекст пересказом конца предыдущего.

Поэтому граница сдвигается к ближайшему концу предложения. Окно поиска
асимметрично — 20 секунд назад против 12 вперёд, и кандидат «после слайда»
дополнительно штрафуется в 1.5 раза, — потому что привычка односторонняя:
лектор объявляет следующую тему и только потом тянется к слайду. Ни один
из двух соседних разделов не может при этом стать короче 15 секунд.

Концом предложения считается точка (или `!`, `?`, `…`) перед пробелом и
заглавной буквой — заглавная буква отсекает сокращения вроде «и т.д. и
т.п.». Точкой заканчиваются только 48% сегментов `.srt`, так что чаще
разрез приходится на середину сегмента: тогда сегмент делится надвое, а
время разреза берётся пропорционально позиции символа в тексте. Пауз в
`.srt` для этого использовать нельзя — whisper подгоняет тайминги встык,
и самая длинная пауза в окне ±25 секунд вокруг границы составляет по
медиане 0.12 секунды.

Результат на тех же десяти лекциях: **48 «рваных» границ из 103 → 1**
(в одном случае подходящего конца предложения в окне не нашлось). Сдвиги
мелкие: медиана −0.6 с, крайние значения −9.8 и +3.1 с, 30 сдвигов назад
против 17 вперёд.

Сдвиг границы меняет и текст раздела, поэтому запись кэша хранит теперь
временной интервал, для которого она сделана, и переиздаются ровно те
разделы, чей интервал изменился (для `01_Introduction` это 4 раздела из
12, ~$0.12). Записи, сделанные до появления интервала, считаются годными,
пока их границы не сдвинулись.

### Анонс новой темы: граница сдвигается ещё на предложение назад

Конец предложения — правильное место для разреза, но не всегда то самое.
Рецензент разобрал случай по файлам `scenes.csv` и `*.srt`: сегмент 470
первой лекции («Этот слайд такой себе. Как бы подытожить бэст практисы в
автоматизации в среде дотнета.») начинается за секунду до появления
слайда Best Practices и заканчивается через одиннадцать секунд после —
и первая фраза попадала в предыдущий раздел, хотя говорит уже о новом.
Привычка та же, что и с концом предложения, только на шаг дальше: лектор
останавливается, объявляет следующую тему и лишь потом тянется к слайду.

Признак анонса собирается из трёх условий, и все три обязательны:

- **остановка.** Пауза не короче 1 секунды перед этой фразой — по данным
  `silencedetect`, а не по `.srt`. Без неё это обычный ритм речи;
- **краткость.** Не длиннее 25 слов и ровно одна фраза между паузой и
  сменой слайда. Длинная фраза — это ещё предыдущая тема;
- **содержание.** Фраза упоминает слайд («Этот слайд такой себе», «Это был
  последний слайд по основной лекции»), содержит оборот перехода («тогда
  предлагаю перейти», «поехали дальше») или называет слово из заголовка
  либо пунктов нового слайда.

Последнее считается по английскому переводу той же фразы — лектор
произносит термины по-русски («бэст практисы»), а слайд написан
по-английски. Слова, которыми названа половина слайдов лекции, из
проверки исключаются: `automation` в курсе по автоматизации не говорит
ничего о том, какой слайд сейчас появится, — остаются `benefits`,
`practices`, `challenges`.

На тех же десяти лекциях правило срабатывает **на 3 границах из 103** — и
ровно там, где на это указывал рецензент: две в первой лекции (Best
Practices, Conclusion) и одна в восьмой («Если нет, тогда предлагаю
перейти к практическому»). Ложных срабатываний нет; строгость здесь
важнее полноты, потому что цена ошибки — фраза, вырванная из своего
раздела.

### Начало подраздела: там, где назван пункт слайда

Оставшиеся замечания по структуре — не про границы разделов, а про
подразделы внутри них: «Test Isolation: the result of one test shouldn't
be depended on the another» — лектор зачитывает пункт слайда, отсюда и
должен начинаться подраздел 6.4, а он начинался парой фраз ниже. Дальше
оглавление плыло: один пункт пропущен, остальные съехали на номер.

Где именно назван пункт — не вопрос суждения, поэтому модель об этом не
спрашивают, а сообщают ей. Слова, которыми один пункт отличается от
соседних по тому же слайду, ищутся в английском переводе речи (лектор
мешает языки — «И последний поинт здесь, что это less adaptability», —
слайд не мешает), а в промпт уходит уже цитата из оригинала. Поиск идёт
сверху вниз: следующий пункт ищется только после того, где нашёлся
предыдущий, иначе случайное упоминание в начале раздела уводит всю
разметку. Правило 4a велит начинать подраздел с этой фразы.

Полнота привязки — сама по себе диагноз, но односторонний:

| раздел первой лекции | привязано | что это значит |
|---|---|---|
| Best Practices in .NET Automation | 8 из 8 | лектор идёт по списку — подразделы уместны |
| Types of Automated Testing | 6 из 7 | то же |
| Key Tools for .NET Automation | 1 из 5 | «Есть три раннера: xUnit, NUnit и MSTest» — одной фразой, разбивать нечего |
| About the Lecturer | 0 из 7 | биография, не список тем |

Заманчиво было решать по этой доле, разбивать раздел или нет, но
проверка на шести уже выпущенных лекциях (50 разделов со слайдовыми
пунктами) показала, что так нельзя: **26 совпадений против 24
расхождений**, и почти все расхождения одного рода — привязка молчит, а
подразделы в документе уместны. На слайде-таблице сравнения Selenium и
Playwright сорок две строки и ни одной привязки, а четырнадцать
подразделов в документе выглядят разумно. Отсутствие привязки не
доказывает, что пункт не обсуждали. Поэтому найденное отдаётся модели как
факт, а решение о разбивке остаётся за ней.

Зато два дефекта проверяются надёжно и стоят дёшево:

- **один подраздел на слайд из нескольких пунктов** — это не разбивка, а
  хвост раздела, которому дали заголовок (в первой лекции так вышел
  подраздел «9.1. Selenium WebDriver и Playwright» при пяти пунктах
  слайда). Такой подраздел сворачивается обратно во вступление —
  детерминированно, без обращения к модели и без потери текста;
- **разобрана большая часть пунктов, но не все** — это ровно то самое
  «оглавление поплыло»: пропущенный пункт сдвигает нумерацию всех
  следующих. Раздел заказывается ещё раз со списком пропущенных пунктов и
  выбором: дать подраздел каждому или вернуть раздел сплошным. Ответ
  принимается, только если он и закрывает пропуск, и не ухудшает покрытие
  текста, — выдуманный подраздел хуже недостающей строки в оглавлении.
  Условие «большая часть» здесь существенно: у слайда-таблицы на сорок
  строк с четырнадцатью подразделами пропуск не считается ошибкой;
- **названы все пункты, а раздел вернулся сплошным** — обратный случай и
  самый показательный. Best Practices первой лекции: восемь пунктов,
  привязаны все восемь, и два прогона подряд модель оставляла десять
  минут речи одним куском, хотя рецензент требовал здесь подразделов
  (замечания 157, 160, 163, 169). Полная привязка — редкость (три
  раздела из 89), поэтому переспросить дёшево, а описывает она ровно то,
  что правило 4 называет списком параллельных пунктов.

После этого раздел 10 первой лекции разбился на все восемь подразделов —
«Изоляция тестов», «Чистый код», «Категоризация тестов», «Непрерывная
интеграция», — каждый начинается с фразы, где пункт назван. Заодно
пришлось уточнить правило 4: заголовок подраздела — это имя пункта в два-
три слова (часть до двоеточия), иначе модель выносит в заголовок весь
пункт слайда целиком.

### Абзацы: по паузам записи, а не по счётчику символов

Абзац — самая частая претензия к первой редакции документа: слишком
длинный, разорванный не там или разорванный там, где рвать нечего. Причина
оказалась простой. Текст, который получал редактор, «разбивался на абзацы»
по паузе в 1.5 секунды между сегментами `.srt`, но whisper подгоняет
тайминги встык, и такая пауза находилась **в 1.2% стыков (75 из 6354)**.
Фактически абзац начинался там, где кончалась очередная тысяча символов:
медиана 160 слов, 70% абзацев длиннее 150 слов, попадались и по 660.

Настоящие паузы при этом никуда не делись — они в аудио. `ffmpeg
-af silencedetect` находит их 350–730 на лекцию (5–11 минут тишины из
часа с небольшим) и тратит на это 2–3 секунды на файл, потому что
декодируется только звук. Ни одного токена это не стоит; результат
кэшируется в сайдкар рядом с видео (см. `silences.py` ниже).

Абзац теперь кончается там, где лектор замолчал:

- рвать можно только на конце предложения;
- короче 45 слов — не рвём вообще;
- дальше требуется тем более короткая пауза, чем длиннее абзац: сразу
  после минимума нужна отчётливая остановка (0.8 с), к 130 словам сойдёт
  любая (0.35 с);
- после 130 слов рвём на первом же конце предложения, была пауза или нет;
- после 200 слов — на первой же паузе, даже посреди «предложения»:
  распознаватель умеет идти на одних запятых по пять минут подряд
  (рекорд — 645 слов без единой точки), а редактор пунктуацию всё равно
  расставит заново;
- после 260 слов не ждём и паузы: рвём на ближайшем стыке сегментов. Это
  случается раз-два на лекцию — там, где нет ни точки, ни тишины, — и
  именно такие куски оставались длиной под 330 слов.

На тех же десяти лекциях: медиана абзаца **160 → 96 слов**, доля длиннее
150 слов **70% → 18%**, самый длинный **660 → 389 слов**, огрызков короче
25 слов было 17, стало 4.

Разбивка исходника — это подсказка, а не приговор: правило 1a промпта
велит её сохранять, но разрешает склеить абзац, разорванный посреди
мысли, и разделить тот, что перевалил за 150 слов или сменил тему на
середине; целевой размер — 50–120 слов. Отдельно оговорены приметы, по
которым абзац открывается («Тогда предлагаю перейти…», «Следующий
пункт…») и закрывается («…и так далее.»). После прогона скрипт бесплатно
пересчитывает готовый текст и сообщает, сколько абзацев всё же длиннее
200 слов и в каких разделах.

Свободой склеивать модель злоупотребляет: в разделе «Benefits of Test
Automation» она свела 11 поданных абзацев к 9, слепив по дороге абзац на
480 слов. Запрет в правиле 1a («не склеивать в абзац длиннее 150 слов, не
оставлять абзац длиннее 200») не помог: в следующем оплаченном прогоне
абзацев-переростков стало не меньше, а больше — семь против пяти.
Поэтому длину абзаца больше не просят соблюдать, а соблюдают: всё, что
после редактирования длиннее 200 слов, режется пополам по ближайшему к
середине концу предложения, и так, пока куски не уложатся в предел. Это
арифметика, а не суждение, и стоит она нисколько. В отчёт после прогона
попадает только то, что разрезать не удалось, — абзац, в котором нет ни
одного конца предложения.

Правила редактирования пронумерованы (`EDIT_RULES_VERSION`): раздел,
отредактированный по старым правилам, переиздаётся, потому что документ
наполовину в одном стиле и наполовину в другом хуже, чем оплаченный
заново. Полное переиздание лекции обходится примерно в $0.39
(`01_Introduction`, 12 разделов), всех десяти — около $4.

### Пунктуация и грамматика: то, чего распознаватель не умеет

45 замечаний из 197 — про знаки препинания и падежи. Промпт и раньше
велел «обогащать пунктуацию» и писать «ё», но проверка готового текста
показала, что ничего из этого не происходит: на 26 тысяч слов
отредактированного текста приходится 0.4 тире и 0.6 двоеточия на тысячу
слов (в сыром транскрипте — 0.6 и 0.0), ни одной точки с запятой,
вопросительных знаков ровно столько же, сколько наставил whisper, а «еще»
встречается 66 раз против 9 «ещё». Расплывчатое правило внутри длинного
абзаца модель просто не выполняет.

Поэтому пунктуация и грамматика вынесены в отдельные правила 1b и 1c с
перечнем конкретных случаев — тех самых, на которые указал рецензент:
тире на месте пропущенной связки («Хотите – посещайте, хотите – нет»),
двоеточие перед перечислением или пояснением, вопросительный знак в
вопросе (в том числе риторическом, на который лектор сама и отвечает),
запятая вместо точки, разорвавшей причину и следствие, точка там, где
одно предложение кончилось, а другое началось, и удаление запятой,
искажающей смысл. Правило 1c — про окончания, которые распознаватель
теряет первыми: «тестировщиков обучают автоматизация», «плюсы, которые
дают нам автоматизацию», «какие-то самолётостроения». Английский перевод
того же места показывает, какое прочтение имелось в виду.

Букву «ё» модели больше не доверяют вовсе — там, где ошибиться нельзя.
Слова, у которых написание через «е» просто не существует («ещё», «её»,
«идёт», «счёт», «чётко», «серьёзно», формы будущего времени на -ём), после
редактирования исправляются кодом: 168 букв на те же 26 тысяч слов,
бесплатно и наверняка. Неоднозначные пары остаются за редактором: «все» и
«всё», «чем» и «чём» — это разные слова, и какое из них имелось в виду,
знает только фраза. Проверке полноты это не мешает: она сравнивает слова,
приведя «ё» к «е».

Тем же способом чинятся два словосочетания, написание которых не зависит
от фразы: «имею ввиду» → «имею в виду» (предлог «ввиду» значит
«из-за» и иметь его нельзя) и «в последствии» → «впоследствии»
(два слова получились бы только в форме «в последствиях»). Рецензент
указал на них пять раз, а в выпуске V07 «ввиду» после формы глагола
«иметь» встречается девять раз из девяти — то есть правило 1c до этих
мест не доходит вовсе, а код исправляет их наверняка.

Насколько вообще доходят точечные правила, теперь измерено. Из 197
замечаний 74 — «голые правки»: рецензент просто написал правильный
вариант рядом с ошибочным, значит, ошибочный можно поискать в новом
тексте механически (`temp/_bare_fix_check.py`). В V07 47 ошибочных
написаний остались дословно, 7 исчезли, про 20 судить нельзя (слишком
частые слова). Осечки распадаются на четыре кучки: английское слово в
русском падеже без дефисного окончания (`benefit-ы`, `quality gate-ов`,
`saving-и` — таких написаний в документе **ноль**), «ввиду» и
«в последствии» (чинятся кодом, 12 мест на документ), расслышанные как
русские слова термины («гид» вместо Git, «темэмбер» вместо team member,
«энтуэнт» вместо end-to-end — глоссарий ловит только то, что в нём
перечислено, зато ловит наверняка: `PlevRite` стал `Playwright` все семь
раз) и согласование падежей, куда модель не вмешивается, храня исходную
формулировку. Дефисное окончание кодом не поставить: какое оно — `-ы`,
`-и` или `-ов` — зависит от слова и падежа, а не от шаблона.

Отдельная история — фрагменты, которые восстанавливает контроль полноты
(см. ниже). Потерянный кусок вырезался из транскрипта пословно, то есть
без единого знака препинания, и модель, которой его давали «починить»,
возвращала ровно такую же россыпь слов: в документ попал абзац на 343
слова, где не было ни одной точки. Теперь кусок вырезается вместе со
знаками, а промпт восстановления требует расставить их так же, как в
основном тексте.

Ещё две бесплатные проверки после прогона: сколько тире, двоеточий и
вопросительных знаков пришлось на тысячу слов, и какие короткие
предложения начинаются с вопросительного слова, но кончаются точкой («Что
это значит на практике.»). Они ничего не чинят, только считают.

Что из этого вышло на `01_Introduction` (три редакции одного документа,
$1.09 за все оплаченные прогоны):

| | до | правила 1b/1c | + разрезание |
|---|---|---|---|
| тире на 1000 слов | 0.1 | 2.0 | 0.4 |
| букв «ё» | 43 | 92 | 82 |
| слов без «ё» там, где она обязательна | 36 | 0 | 0 |
| медиана абзаца | 73 | 97 | 98 |
| самый длинный абзац | 452 | 480 | 199 |

Детерминированное держится намертво, а пунктуация гуляет: два прогона по
одному и тому же промпту дали 14 тире и 3 тире на один и тот же текст.
Поэтому плотность знаков теперь печатается после каждого прогона — это
единственный способ заметить, что редактор в этот раз поленился.

### Контроль полноты: пропуски и дубли

Модель, редактируя раздел, иногда молча теряет фразу (чаще всего —
пограничную: последние предложения раздела уже вводят тему следующего
слайда, и модель считает их «чужими») или, наоборот, выдаёт один и тот же
фрагмент дважды — во вступлении раздела и ещё раз в подразделе, которому он
принадлежит. И то, и другое ловится автоматически.

Отредактированный текст **на языке оригинала** сравнивается пословно
(`difflib`) с тем фрагментом транскрипта, из которого он сделан:

- цепочка от 5 подряд идущих слов оригинала, которой в результате нет
  вообще, считается потерянным содержанием (более короткие пропуски — это
  нормальная чистка слов-паразитов и оговорок);
- совпадающий фрагмент от 12 слов между вступлением и подразделом (или
  между двумя подразделами) считается дублем.

Английская версия так не проверяется: это машинный перевод, который
редактор переписывает гораздо свободнее, и пословное сравнение дало бы
сплошные ложные срабатывания.

Раздел редактируется одним вызовом, пока его отредактированный текст
укладывается в ~7000 токенов ответа (это ~15 минут речи, т.е. практически
любой раздел по слайду). Более длинные — фактически только единственный
раздел видео без слайдов и таймкодов — режутся на части по этой границе и
склеиваются; части всегда сплошные (без подразделов), и именно на их стыках
теряется текст, поэтому резать раньше времени невыгодно.

Дальше — четыре ступени:

1. найденные фрагменты возвращаются модели, и раздел редактируется ещё раз
   («вот что ты потерял; вот что выдал дважды»); из двух попыток остаётся
   лучшая — повтор бывает хуже того, что чинит;
2. если не помогло — точечная починка, по одному вызову на проблему:
   потерянный фрагмент редактируется отдельно (модель получает только его,
   английский текст раздела и соседние абзацы) и вставляется на своё место
   в списке абзацев; продублированный — удаляется из вступления раздела,
   подразделы сохраняют свою копию. Результат принимается, только если
   проверка стала лучше, иначе откат;
3. если после этого не хватает **пятой части раздела и больше** — раздел
   редактируется заново по частям примерно по 1200 токенов, как длинные
   разделы выше. Части возвращаются сплошными (без подразделов) и
   принимаются, только если несут больше текста, чем целый раздел;
4. что осталось — печатается в лог (`WARNING`, с началом каждого фрагмента)
   и записывается в кэш, чтобы следующие запуски не оплачивали заведомо
   безуспешное редактирование того же раздела снова.

Ступень 2 нужна потому, что переиздание всего раздела почти не возвращает
фразу, которую модель сочла чужой (обычно это последние предложения
раздела, уже вводящие следующий слайд): попросишь тот же раздел целиком —
получишь то же решение. Тот же фрагмент, заказанный отдельно, редактируется
без возражений.

Ступень 3 — про другую беду, и точечная починка с ней не справляется.
Иногда модель добросовестно редактирует начало раздела и сворачивает всё
остальное: в лекции про Reflection из раздела на 7,6 минуты в документ
попало 450 слов из 1330, а на просьбу вернуть потерянные 878 слов одним
куском модель свернула их второй раз. Разница между «потеряна фраза» и
«потерян хвост» здесь и проходит по одной пятой раздела: части,
достаточно короткие, чтобы модель дочитала их до конца, — единственное,
что помогает. Плата за это — подразделы такого раздела (части всегда
сплошные), и берётся она только после того, как всё остальное не помогло.

Разделы, отредактированные более ранними запусками (в кэше нет отметки о
проверке), проверяются офлайн — бесплатно. Не прошедшие проверку удаляются
из кэша, попадают в оценку стоимости отдельной строкой и редактируются
заново; остальные помечаются как проверенные. Раздел, у которого в кэше
записана потеря от пятой части и больше, тоже редактируется заново — один
раз: к нему теперь применима ступень 3, и в кэше остаётся отметка
`split_tried`, чтобы второй раз за то же не платить. Поэтому уже готовый
документ можно починить, не оплачивая видео целиком:

```bat
python src\create_final_docs.py IT\_Autotesting lectures --video 01_Introduction --force
```

### Результаты

В `<ЯЗЫК>/OUTPUT/` (например, `RU/OUTPUT/` и `EN/OUTPUT/`) — три файла:

- `<имя>.md` — оглавление (Table of Contents) со сквозной нумерацией всех
  уровней (1., 2., 2.1.); строки тела не длиннее 80 символов, без
  переносов в словах, выравнивание по правому краю добавлением пробелов
  внутри строки (одинарный пробел может стать двойным, но не более);
  абзацы разделяются пустыми строками; текст слайдов — цитатами (`>`);
- `<имя>.docx` — стили по шаблону `--doc` (или встроенные); оглавление —
  настоящее поле Word TOC: пункты являются гиперссылками внутри документа,
  справа — номера страниц с отточием (независимо от источника оглавления —
  слайды или таймкоды). Файл просит Word/WPS обновить поля при открытии;
- `<имя>.pdf` — печать .docx через WPS Writer (если WPS Office установлен —
  без сбоев активации и без конфликтов с Word, открытым пользователем),
  иначе через Microsoft Word (COM); перед экспортом поля (оглавление)
  обновляются, поэтому в PDF оглавление кликабельно и с номерами страниц.
  Конвертация выполняется в отдельном дочернем процессе, поэтому сбой COM
  (access violation) не убивает весь запуск: попытка повторяется. Для пути
  через Word действуют прежние защиты: экземпляр Word, оставшийся от сбойной
  попытки, снимается автоматически (Word, открытый пользователем, не
  затрагивается); из реестра (`HKCU\…\Word\Resiliency`) удаляются записи о
  «проблемности» конвертируемого файла и маркеры сбойного старта; модальные
  диалоги Word закрываются автоматически («Нет»/«Отмена»). PDF — «best
  effort»: если конвертация не удалась, документ считается обработанным
  (md+docx), а недостающие PDF автоматически досоздаются из готовых .docx
  при следующем запуске скрипта — без затрат на API («PDF backfill»).

В русской версии заголовки разделов остаются английскими (по ним видно
соответствие слайдам), заголовки подразделов переводятся на русский,
дословный текст слайдов не переводится.

Автоматизация: `_channels/<канал>/_run_scripts/create_final_docs.bat`
(лог — в `_run_scripts/_logs/`).

Связка «транскрибирование с YouTube → финальное редактирование» одним запуском:
`_channels/_VladilenMinin/_run_scripts/transcribe_and_edit.bat` — очередное
видео плейлиста «Старт IT карьеры с НУЛЯ в 2025» транскрибируется прямо с
